# 模型/AI 功能评测方案设计

## 任务分流

1. **离线评测**:上线前判断能力好坏、对比候选模型 → 走默认工作流。
2. **上线验收**:给一个功能定"达到什么标准可以上线" → 走默认工作流,但阈值必须绑定发布决策(达标放量/不达标阻塞)。
3. **线上监控**:功能已上线,要持续观测 → 重点在自动指标 + 抽样人评的组合,以及告警阈值。
4. **badcase 归因**:已有一批差的输出要分析 → 跳过指标设计,先聚类错误类型、统计占比、定位每类的可能原因,产出修复优先级。

## 开始设计之前必须确认的信息

1. 评测对象是什么(单个模型?端到端功能?prompt 改动?)
2. 拿评测结论做什么决策(选型/上线/回归?)——决策不同,方案的严格程度完全不同
3. 有没有已有的样例集和历史指标
4. 评测预算:能投入多少人工标注,有没有可用的自动化手段

## 默认工作流

按顺序执行,顺序本身就是方法:

1. **先收集 badcase,再定指标**。找 20~50 条真实的差输出(来自内测、竞品、用户反馈),按错误类型聚类。指标应该从错误类型长出来,而不是从文献里抄。没有真实样例时,先构造典型输入自己跑一批。
2. **把"好"拆成可独立打分的维度**。生成类任务通常拆为:事实准确性、完整性、相关性、表达质量、安全合规。每个维度单独定义打分标准,不要用一个总分掩盖问题。
3. **构建样例集**。明确数量、来源、场景覆盖(常规/边界/对抗),并留一部分不参与调优的封闭集。样例集是评测方案的核心资产,没有样例集的方案不算完成。
4. **为每个指标选评测方式**,默认优先级:可自动计算的客观指标 > 大模型评审(需先用人工标注校准一致性) > 纯人工双标。写明每种方式的成本和局限。
5. **定阈值和决策规则**。每个指标给出阈值、达标/不达标分别触发什么动作、由谁拍板。
6. **设计回归机制**。模型/prompt 每次变更后,封闭集必须重跑,明确对比基线是什么。

指标设计细节与常见陷阱见 `references/metrics-checklist.md`,按需读取。

## 产出前自查清单

- [ ] 每个指标都能追溯到一类真实错误,而不是"看起来该测"
- [ ] 样例集有数量、来源、场景覆盖说明,且有封闭集
- [ ] 用大模型做评审的指标,写明了与人工标注的校准方式
- [ ] 每个阈值都绑定了决策动作(放量/阻塞/告警)
- [ ] 方案里没有"效果好""质量高"这类不可执行的表述

## 边界

- 本 skill 产出评测方案文档,不负责实现评测代码
- 若评测结论要写回需求文档,配合 `ai-prd-author` 使用
- AB 实验的统计设计(样本量、显著性)超出本 skill,需要时提示用户找数据团队确认
