# AI 功能 PRD 撰写

## 任务分流

先判断任务属于哪一类,再进入对应流程:

1. **新功能 PRD**:从零定义一个 AI 功能 → 走完整流程。
2. **迭代 PRD**:在已有功能上加能力或换模型 → 先要现状(当前指标、已知 badcase),只写增量,重点是回归风险。
3. **PRD 评审**:用户给了一份文档让你提意见 → 不重写,按"自查清单"逐项挑问题,输出问题列表和修改建议。

## 开始写之前必须确认的信息

缺任何一项,先向用户提问,不要自行假设:

1. 目标用户和触发场景(用户在什么情况下用到这个功能)
2. 功能的输入和输出是什么(输入:文本/图片/多轮对话?输出:结构化/自由文本?)
3. 有没有已知的模型能力约束(延迟、成本、可用的模型、数据合规要求)
4. 上线判断权在谁(有没有既定的验收指标或流程)

## 默认工作流

按顺序执行,不要跳步:

1. **定义用户问题**:一句话写清"谁,在什么场景,现在怎么解决,痛在哪"。写不出来就说明信息不够,回去提问。
2. **定义能力边界**:明确"这个功能保证做好什么、明确不做什么、做不好时表现是什么"。AI 功能必须有"做不好"的预案,这一节不可省略。
3. **设计交互与兜底**:主流程之外,必须覆盖三种情况——模型输出错误/低质量时用户怎么办、响应超时怎么办、用户不满意如何反馈或重试。
4. **定义数据需求**:需要什么数据做 prompt/微调/评测,数据从哪来,有无合规风险。
5. **定义评测验收标准**:必须包含可执行的三件套——评测样例集(数量、来源)、指标及阈值、评测方式(人工/自动/AB)。只有形容词没有数字和样例集的验收标准视为未完成。若评测方案本身很复杂,建议用户单独走 `model-eval-design` skill。
6. **列出发布计划**:灰度范围、观测指标、回滚条件。

完整章节模板见 `references/prd-template.md`,按需读取。

## 产出前自查清单

交付前逐条自查,任何一条不满足就先修:

- [ ] 每个功能点都能回答"用户为什么需要它",而不是"模型能做到所以加上"
- [ ] "能力边界"一节明确写了不做什么、做不好时的表现
- [ ] 兜底策略覆盖了错误输出、超时、用户不满三种情况
- [ ] 验收标准里有样例集数量、指标阈值、评测方式,三者齐全
- [ ] 没有出现"体验良好""效果达到预期"这类不可验证的表述

## 边界

- 本 skill 不做技术方案设计(模型选型、架构),只在 PRD 中记录约束
- 评测方案的详细设计交给 `model-eval-design`
- 竞品对比只写结论,详细拆解交给 `competitive-teardown`
