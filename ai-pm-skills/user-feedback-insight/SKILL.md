# 用户反馈聚类与需求提炼

## 任务分流

1. **全量梳理**:一批新反馈,要求整体结论 → 走默认工作流。
2. **专项追查**:带着假设来查("是不是很多人抱怨生成速度?") → 先按假设筛选和计数,再看筛剩下的反馈里有没有推翻假设的信号,两边都要报告。
3. **周期对比**:和上一批反馈比变化 → 沿用上一次的分类体系,不要重新发明分类,重点报告新增类别和占比变化。

## 开始之前必须确认的信息

1. 反馈的来源和时间范围(不同渠道的用户群体偏差很大,结论必须注明来源)
2. 数据量级(几十条逐条读;上千条先抽样定分类体系,再全量归类)
3. 这次分析要支持什么决策(排优先级?定位一次事故?写复盘?)

## 默认工作流

1. **先读原始反馈,再建分类**。至少通读 30~50 条原文再动手分类,禁止直接套"性能/功能/体验"这类万能框架——分类必须从这批数据里长出来。
2. **区分"用户说的"和"用户要的"**。每条反馈拆成两层:表面诉求(用户的原话)和底层问题(用户实际卡在哪)。例:"希望能重新生成"的底层问题可能是首次生成质量差。
3. **聚类并计数**。每个类别给出:名称、界定标准、条数与占比、2~3 条原声引用。原声必须保留,这是说服团队的最强证据。
4. **标注严重度,不只看数量**。少量但致命的反馈(数据丢失、事实错误引发投诉)要单独提级,不能淹没在计数里。
5. **产出决策建议**。每个主要类别给出:建议动作(修复/深挖/观察)、影响面估计、建议优先级及理由。区分事实(数据)与判断(你的推断),标注清楚。

## 产出格式

- 一段话总结(最大的 1~2 个信号)
- 分类明细表:类别 | 占比 | 严重度 | 原声引用 | 建议动作
- 与决策相关的开放问题(数据不足以回答、需要进一步调研的)

## 产出前自查清单

- [ ] 分类是从这批数据归纳的,不是套的通用框架
- [ ] 每个类别都有原声引用
- [ ] 低频高危问题被单独提级,没有被占比掩盖
- [ ] 结论注明了数据来源、时间范围和渠道偏差
- [ ] 事实与推断分开表述

## 边界

- 本 skill 处理定性反馈文本,不做埋点数据分析
- 提炼出的需求要落成文档时,交给 `ai-prd-author`
- 若反馈指向模型质量问题,badcase 深入归因交给 `model-eval-design` 的归因流程
