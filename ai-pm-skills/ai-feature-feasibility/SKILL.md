# AI 功能可行性评估与降级设计

## 任务分流

1. **想法初筛**:一句话的点子,判断值不值得投入 → 走默认工作流,产出"做/不做/先验证"三选一的明确建议。
2. **方案比选**:同一目标下比较不同实现路径(大模型/小模型/规则/人工) → 重点填"路径对比表",按质量、成本、延迟、可控性、迭代速度五个维度打分。
3. **风险审查**:方向已定,上线前过一遍风险 → 跳到"风险清单"一节逐项过。

## 开始之前必须确认的信息

1. 用户任务和当前替代方案(用户现在不用 AI 是怎么完成的)
2. 错误的代价:功能输出错了,用户损失多大?能不能被用户发现和纠正?
3. 规模与预算:预期调用量、可接受的单次成本和延迟
4. 有没有可用的数据(评测用、优化用)

## 默认工作流

1. **先评"值不值",再评"能不能"**。第一问永远是:这个任务用户做的频率和痛感够不够高?AI 相比现有方案的提升是数量级的还是边际的?如果价值不成立,技术可行性不用评了,直接建议不做。
2. **给任务定容错等级**,这是 AI 功能可行性的核心变量:
   - 高容错(灵感、草稿、推荐):输出差了用户自己会筛 → 对模型要求低,可行性通常高
   - 中容错(摘要、描述、分类):错误会被使用但可纠正 → 需要质量验收和纠错交互
   - 低容错(资金、医疗、自动执行的操作):错误直接造成损失 → 默认建议"AI 辅助 + 人工确认"架构,纯自动方案要明确反对并说明理由
3. **评估技术路径**:当前模型能力对这个任务是"轻松胜任/踮脚够到/超出能力",给出判断依据(类似任务的公开表现、自己实测)。能实测就构造 10 组典型输入快速实测,实测半天胜过讨论一周。
4. **算成本账**:单次调用成本 × 预期调用量,加上评测和标注的人力成本,和收益放在一起看。
5. **设计降级链路**:模型不可用或质量不达标时退到什么(缓存/规则/隐藏功能),降级本身也是可行性的一部分——没有可接受的降级方案,低容错功能不建议上。
6. **产出最小验证方案**:如果结论是"先验证",给出:验证什么假设、用多少样例、什么结果算通过、预计投入。验证方案要小到一两周内能出结论。

## 风险清单

逐项确认并写明缓解措施:幻觉与事实错误、数据隐私与合规、内容安全、成本失控(调用量超预期)、延迟不达标、模型供应商依赖、用户预期管理(过度承诺)。

## 产出格式

- 结论:做 / 不做 / 先验证(三选一,不许含糊)
- 判断依据:价值评估、容错等级、技术路径判断、成本估算
- 若"先验证":最小验证方案
- 风险清单及缓解措施

## 产出前自查清单

- [ ] 结论是三选一的明确建议,并给出了最关键的一条理由
- [ ] 容错等级有明确判定,低容错任务有人工确认环节的设计
- [ ] 成本估算有量级数字,不是"成本可控"
- [ ] 有降级方案
- [ ] "先验证"的方案能在两周内出结论

## 边界

- 本 skill 输出决策建议和验证方案,不做详细技术架构设计
- 结论为"做"之后的需求撰写交给 `ai-prd-author`,验收标准设计交给 `model-eval-design`
